# Анализ оптимизаций MoonModules (WLED-MM) и план заимствований для форка WLED-LightMusic

**Дата анализа:** 2026-09-02
**Наша база:** upstream WLED `v16.0.1` (2026-07-07, ESP-IDF v4.4.8 / arduino-esp32 2.0.18)
**Сравнивалось с:** WLED-MM `v14.7.1` (2026-01-13, база upstream 0.14) + ветка `mdev` + внешний репозиторий `MoonModules/WLED-AudioReactive-Usermod` (актуальный аудио-код MM, июнь 2026)

---

## 1. Ключевой стратегический вывод

Политика ТЗ («не переносить MoonModules целиком, брать только изолированные фичи») подтверждена фактами и даже усилилась:

1. **WLED-MM застряла на базе upstream 0.14** и не перебазировалась; развивается медленно (релиз-майлстоуны 14.7.3/14.8.1 просрочены), центр тяжести MoonModules сместился в новый проект **projectMM** (написан с нуля, мультиплатформенный).
2. **ESP8266 в MM официально deprecated** («we're saying goodbye to 8266», 14.7.1) — для наших 8266-нод из MM брать нечего; все полезные фиксы 8266 живут в upstream (и уже в v16).
3. **Основной «золотой фонд» MM уже поглощён upstream** — во многом руками тех же людей (softhack007, netmindz, willmmiles состоят в обеих командах). Мы получили это бесплатно вместе с v16.0.1.
4. Аудио-код MM вынесен в отдельный репозиторий `WLED-AudioReactive-Usermod` (2 файла) — это резко упрощает точечный перенос: не нужно копаться в ядре MM.

## 3. Рекомендованные cherry-pick'и (по приоритету для нашего сценария)

Наш сценарий: ESP32-master с INMP441 → UDP (часто через SoftAP) → до 8 нод (ESP8266 1D + ESP32/C3 2D), Audio Feature Sync — следующий этап. Оценка: ⭐ малый патч / ⭐⭐ средний / ⭐⭐⭐ большой.

### Приоритет A — прямо усиливает Audio Feature Sync (FR-4 режим B)

1. **Надёжность приёма UDP Sound Sync** ⭐⭐ — `frameCounter` в зарезервированном байте 17 пакета V2 + sequence-check (отбрасывание дубликатов/переупорядоченных, rollover-safe) + **purge-очереди** на приёмнике (обрабатывать только последний пакет — критично для медленного loop ESP8266). Формат остаётся бинарно совместимым 44-байтным V2 — upstream-приёмники просто игнорируют эти байты. Это ровно та «sequence/version»-защита, что уже заложена в FR-4.
2. **Broadcast вместо multicast (опция)** ⭐ — отправка на subnet-broadcast вместо 239.0.0.1. Multicast через SoftAP ESP32 печально известен потерями; для роя из 8 нод на нашей же точке доступа это может резко поднять надёжность. ~15 строк + чекбокс (PR #10 внешнего репо MM). Требует проверки приёма на 8266.
3. **Событийная отправка аудиопакета** ⭐ — слать сразу по готовности FFT-результата, а не по таймеру 20 мс (минус ~10 мс латентности).
4. **Частотные профили INMP441** ⭐ — таблица `fftResultPink[11][16]` с профилями 2–4 специально под INMP441 (datasheet / бас / голос) вместо единственной фиксированной пинк-таблицы upstream. Прямое улучшение баланса GEQ именно для нашего микрофона.

### Приоритет B — качество аудио на master

5. **DC-blocker (`useInputFilter=2`)** ⭐ — универсальный low-cut ~40 Гц, чище низ у INMP441 (~25 строк, изолировано).
6. **micLevelMethod (freeze нуля микрофона)** ⭐/⭐⭐ — устраняет «проседание» баса из-за плавающей оценки тишины.
7. **micQuality** ⭐ — меньше сглаживания для качественных цифровых микрофонов.
8. **I2S: DMA 24 буфера + IRAM/LEVEL2-3 флаги прерываний** ⭐ — меньше пропущенных сэмплов при загруженном Wi-Fi (наш master одновременно SoftAP на 8 клиентов!). Несколько строк конфига, но обязателен прогон на железе.

### Приоритет C — системные и сборочные

9. **Флаги компиляции: `build_unflags = -Os` + `-O2` + `-funsafe-math-optimizations`** ⭐ — самый дешёвый пункт (чисто platformio.ini). Риски: рост прошивки (у node ESP8266 flash уже 81%! — применять только к ESP32-профилям), незначительные визуальные отличия float-эффектов. У MM замер: +10% на S3.
10. **Heap-мониторинг по largest-free-block** ⭐ — `getContiguousFreeHeap()` как метрика фрагментации + двухступенчатая деградация (MIN_HEAP → чистка сегментов, MIN_HEAP_CRIT → reconnect).
11. **Ожидание простоя ленты перед записью FS + пауза LED при OTA** ⭐ — убирает глитчи при сохранении cfg/presets и при OTA (≤30 мс ожидания).
12. **Debug-инструментация loop** ⭐ — замер usermod/strip времени, «Slow strip»-предупреждения, loops/sec каждые 30 с. Под `#ifdef WLED_DEBUG`.

### Приоритет D — отложить / по потребности

- **Sliding-window FFT + WLEDMM_FASTPATH (~86 Гц обновления GEQ)** ⭐⭐⭐ — самый «размазанный» пункт (приоритет задачи FFT=4, speed-коррекции фильтров, тайминги, отправка). Годами помечен в MM как experimental. Рассмотреть только после нагрузочных тестов Audio Feature Sync с 8 нодами, целиком.
- **FFT_MAJORPEAK_HUMAN_EAR + сглаженный MajPeakSmth** ⭐⭐ — «человеческое» взвешивание доминирующей частоты; полезно, если частотные эффекты на нодах будут выглядеть нервно.
- **soundPressure / zeroCrossingCount** ⭐⭐ — дополнительные признаки в reserved-байтах V2; брать, если понадобятся эффектам.
- **Кодеки WM8978 / AC101 / ES8311** ⭐ — самодостаточные классы (I2C-init + case в switch); пригодятся для будущего AUX (FR-8), но ES8388/ES7243 уже есть в upstream — начинать с них.
- **UDP realtime speedup (DDP/Art-Net)** — не про наш notifier-sync; отложить до P7 (DMX/DJ).
- **`#define yield() {}` из FASTPATH** — **не брать**: рискованно для fairness задач, у нас master и так нагружен SoftAP+FFT+WS.

## 4. Чего НЕ делать (проверенные тупики)

- Не перебазироваться на MM и не тащить их FFT-библиотеку (arduinoFFT-форк) — у нас ESP-DSP быстрее.
- Не брать NeoPixelBus-пины версий MM (2.7.9 — старее v16).
- Не класть LED-буферы в PSRAM.
- Не искать в MM ничего для ESP8266 — платформа там мертва.
- Не переносить MM-реализацию HUB75/PSRAM-webserver — плохо изолированы от их ядра (для 2D-нод у нас upstream v16 HUB75 уже есть).

## 5. Предлагаемый порядок работ

1. Вместе с реализацией Audio Feature Sync (следующий этап по ТЗ): пункты 1–4 приоритета A — они определяют формат пакета и надёжность, дешевле заложить сразу, чем ретрофитить.
2. Отдельным малым PR: приоритет C (флаги сборки — только ESP32-профили, heap, FS/OTA-глитчи, debug-инструментация) + host-тесты, где применимо.
3. По результатам полевых тестов с INMP441: приоритет B.
4. Приоритет D — только по фактической потребности после нагрузочного теста 8 нод.

Каждый перенос — по правилам §3 ТЗ: изолированный патч, сборка обоих (теперь трёх) профилей, host-тест при наличии логики.
